## Correcciones de `/revisar`

Hallazgos del subagente `revisor` y de la revisión propia, todos corregidos en un commit `fix` en
la misma rama:

1. **Bloqueante:** una variable definida dos veces hacía que el bootstrap pisara la clave real.
   Ahora `parseEnv` rechaza duplicados con `ConfigError`. Test:
   `stops on a set key followed by a pasted empty duplicate, leaving the file as it was`.
2. Claves con la forma correcta pero inválidas: el esquema revisa el checksum de StrKey y el rango
   de secp256k1, y las direcciones se derivan antes de escribir. Comprobado a mano antes del
   arreglo, sin usar ninguna clave real:
   ```
   stellar: Error "invalid checksum"
   evm: Error "expected valid private key: 1 <= n < 115792…494337, got 0"
   ```
   viem cita la clave en el mensaje. Por eso el error del SDK no se encadena como `cause`.
3. Rust fijado en `1.98.0`. Además, los scripts de la raíz no lo respetaban: rustup lee el
   toolchain de la carpeta actual, no del `--manifest-path`. Ahora entran con `cd`:
   ```
   $ cd contracts/stellar && rustup show active-toolchain
   1.98.0-aarch64-apple-darwin (overridden by '…/contracts/stellar/rust-toolchain.toml')
   $ pnpm run contracts:build:stellar
       Wasm Hash: 0e69f92bba7e821220a29392211286eace562681412020bc249ff53130664ad9
   ```
   Es el mismo hash que con `stable`.
4. El entrypoint pasó a `runBootstrapCli`, con tests para tres casos: un `AgentHabitError` que cita
   una clave (se omite), un error de dependencia (solo dice "unexpected failure") y un fallo
   normal (código y mensaje).
5. Esta evidencia: salidas completas o marcadas con `…`.
6. El README da los comandos exactos de `stellar-cli` 28.1.0 y Foundry 1.8.5.
7. `cargo test --locked` también en local.
8. Escritura de claves: se borra la copia temporal si la escritura falla, y un lock con pid
   impide dos bootstraps a la vez. Si el lock quedó de una corrida muerta, se retoma.
9. El usuario de prueba se elige por su variable, no por su posición.
10. Los tests usan `isAgentHabitError` en vez de casts.

Después de las correcciones, una cuarta corrida contra testnet con las claves reales: pasan la
validación nueva (sin duplicados, checksum y rango válidos), no se movió nada y el lock no quedó
en la carpeta.
